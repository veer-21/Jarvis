# JARVIS Agent Architecture

This document describes the role, responsibilities, inputs, and outputs of the specialized agents within JARVIS v3.0. All agents subclass `BaseAgent` and communicate asynchronously or synchronously using `AgentMessage` objects via the `AgentBus`.

---

## 1. Commander Agent (`CommanderAgent`)

* **Role**: Primary system entry point and request router.
* **Responsibilities**:
  * Receives initial natural language input from the user (via CLI, API, or Voice).
  * Classifies intent into: `task` (complex planning/execution), `command` (local fast-path execution), `query` (simple system questions), or `chat` (general discussion).
  * Determines if the request is low risk or requires routing to high-level executors (like the `ExecutionManager` / `GoalExecutor`).
* **Input**: User request string wrapped in an `AgentMessage`.
* **Output**: `AgentResponse` indicating success, output content, and intent classification metadata.

---

## 2. Security Agent (`SecurityAgent`)

* **Role**: Safety gatekeeper and risk assessor.
* **Responsibilities**:
  * Inspects proposed shell commands, Python scripts, or custom automation parameters.
  * Grades commands by risk levels: `SAFE`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
  * Gates high-risk commands and triggers interactive confirmation requests (Human-in-the-Loop) before tool execution.
* **Input**: Code block or command string in `AgentMessage` with action `assess_risk`.
* **Output**: `AgentResponse` containing safety classification (`RiskLevel`) and recommendation metadata.

---

## 3. Memory Agent (`MemoryAgent`)

* **Role**: Persistent context and experience manager.
* **Responsibilities**:
  * Manages long-term semantic knowledge in ChromaDB/JSON storage.
  * Scores conversation turns for long-term relevance using keyword and length signals to prevent memory pollution.
  * Creates episodic summaries from conversation blocks to reduce context usage.
  * Auto-updates project memory files when task history is compiled.
* **Input**: Conversational context, task outcomes, or queries wrapped in `AgentMessage` with actions `store`, `retrieve`, `summarize`, or `update_project_brain`.
* **Output**: `AgentResponse` with retrieved context snippets, storage confirmation, or update reports.

---

## 4. Operator Agent (`OperatorAgent`)

* **Role**: Hands-on action execution engine.
* **Responsibilities**:
  * Interacts directly with system tool layers (file systems, terminal, web tools, desktop, and Playwright browsers).
  * Safely executes individual tool calls generated by planning processes.
  * Handles exceptions, retries, and formatting of raw tool outputs.
* **Input**: Executable tool requests with parameters and execution constraints.
* **Output**: `AgentResponse` containing the text/structured results of the execution.

---

## 5. Refiner Agent (`RefinerAgent`)

* **Role**: Self-improving workflow optimization optimizer.
* **Responsibilities**:
  * Scans task memory logs to detect repetitive workflows or frequently run shell scripts.
  * Uses the LLM to write custom Python scripts that bundle these repetitive tasks into clean, reusable tools.
  * Saves generated tools to `tools/custom/` and triggers dynamic reloading in the `ToolRouter`.
* **Input**: Optimization triggers or task history lists.
* **Output**: `AgentResponse` indicating whether a new tool was generated, its name, and registration status.
